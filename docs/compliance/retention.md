# Retention schedule

What is kept, for how long, what ends it, and whether the deletion is automated yet. The public privacy notice (`/privacy`, "How long we keep it") states the same periods; change this file first, then the page and `PRIVACY_NOTICE_UPDATED` in `webapp/lib/site.ts`.

"Automated" means code in this repo enforces it today: the daily Convex cron `retention-daily` (04:15 UTC, `webapp/convex/retention.ts`; one paginated walk per rule, all with one clock) or the pipeline command `camsocs prune-cache`. Everything marked **manual** is Joshua's job; the reason is given.

| ID | Data | Kept for | Ends with | How it is removed | Automated? |
|---|---|---|---|---|---|
| R1 | Organisation listings (`organisations`, `orgCards`, teams, sessions) | While the organisation is active | No activity and no current register for 2 academic years → marked defunct, so `archived` (left out of the directory's default view), then deleted 1 year later. A removal request ends it at once (R8) | Status is derived daily (`convex/derive.ts`: `dormant` after 180 days without activity or a current registration; `archived` once defunct). Deletion: `ingest/purge:removeEntity` | `dormant`: yes. Archiving and deletion: **manual** — the first harvest was in October 2026, so nothing can be due before July 2028, and deleting a listing is a judgement call (a quiet society is not a defunct one) |
| R2 | Provenance (`fieldClaims`, `sources`). `fieldClaims.valueRaw` holds the unredacted original of public free text (D1), names included | As long as the entity it describes; the original of a superseded free-text reading only until a newer reading replaces it | Entity deleted; a newer reading | Deleted with the entity (`ingest/purge:removeEntity`); an event's claims go with the event (R3); a superseded free-text claim's `valueRaw` is cleared when it is superseded (`ingest/claims.ts`, DPIA-lite R-12) | With R1: **manual**. With R3 and supersession: yes |
| R3 | Events (`events`, `eventOrganisers`), stored event images | 1 year after the event ended (longer than the 180-day activity window that `lastActiveAt` needs) | Age | `purgeEvents`: the event, its claims (in pages of at most 2,000 per call; the event goes only once none is left) and organiser links; its stored image (and `storedFiles` row) unless another event or a logo still shows it; its organisers are re-derived | **yes** |
| R4 | Mailing-list messages (`inboundEmails`, their stored HTML and attachments), the mail's words quoted in its events' claims, the model's replies about it and its staged events | Body (text, HTML, attachments) and its words elsewhere: 30 days from receipt once processed. The row (sender, subject, extraction outcome): 90 days from receipt | Age; extraction finished | `stripMailBodies` empties the body, deletes the files (`bodyDeletedAt`) and clears the quotes and originals of every claim sourced `inbound:<message-id>`; `purgeMail` deletes the row and anything left in storage, processed or not — a mail its events cite stays as a stub (message id, list, receipt time, organisation, event keys; no sender, subject or text, `purgedAt`). On the pipeline host `prune-cache` (after every scheduled run) deletes the `email_events_v1` / `image_events_v1` replies, the calendar-noise verdicts and name redactions of mail-derived readings (cached apart as `event_noise_v2.mail` / `redact_names_v2.mail`) and `mailing_list_email` staging after 30 days | **yes** |
| R5 | Named committee members (`people`) | Until `staleAfter` (the next 30 June, D2) + 30 days, unless the person consented to longer | Handover date | `stale` set daily (`convex/derive.ts`); `expirePeople`: past `staleAfter`, the broker's own rows are archived (the 30-day grace, in which the broker may extend `staleAfter`); 30 days past it every row is deleted, from public sources or the broker's own, and its key is remembered (`expiredPeople`: key and academic year only) so a page that still lists last year's committee does not add it back; a re-sighting never moves `staleAfter` forward unless the source states a later academic year. Rows with `consentBasis: consent` stay | **yes** |
| R6 | Interactions and introductions | 3 years after the last interaction with that organisation | Age | `purgeInteractions`: an interaction 3 years old whose organisation has had none since; `purgeIntroductions`: introductions 3 years old | **yes** |
| R7 | Raw page cache (`var/cache/`), LLM inputs/outputs kept locally, staged observations (`var/staging/`), the pipeline host's run logs | 90 days | Age | `pixi run prune-cache` (`camsocs prune-cache --older-than 90d`): a page's body, meta and failure note go together once all are older; LLM replies one by one; superseded staging files, never the latest of each part. Run logs on the VPS (`/var/log/camsocs/`) are removed by logrotate at 90 days | **yes** on the VPS host: every scheduled run (daily and weekly) ends with `prune-cache` (`docs/ops-vps.md`, D5); on the laptop, when the command is run |
| R8 | Listing requests (`listingRequests`) | 2 years after resolution; a rejected request 90 days after it was rejected | Age | `purgeRequests` deletes the row — an accepted correction, which its `owner_submitted` claims cite, is reduced to a stub (key, kind, listing, role, outcome, dates; no submitter address, message or fields, `purgedAt`). Accepting a removal or objection creates **suppressions** (`suppressions`: the listing's key, a field name, an address only as a sha256, or a broker person's key; date and request kind), kept indefinitely: the pipeline filters by them before every load, and Convex refuses what slips through (`convex/lib/suppressions.ts`). The claims a suppression sets aside keep no value, original or quote (`setAsideBy`); lifting it deletes them | **yes** |
| R9 | Sign-in accounts and sessions (Better Auth) | Sessions: until expiry. Accounts: until deletion is requested, or 2 years unused | Expiry; request; inactivity | Better Auth expires sessions; account deletion by hand | Sessions: yes. Accounts: **manual** — they live in the Better Auth component's tables, which only its adapter should write; nobody but Joshua signs in before the `@cam.ac.uk` tier opens |
| R10 | Run log (`harvestRuns`) | 1 year | Age | `purgeRuns` | **yes** (no personal data) |

## Annual review (each July)

1. Refresh every listing from its sources (`pixi run harvest`); anything no source still lists becomes a candidate for archiving (R1).
2. Check that `retention-daily` ran (Convex dashboard, scheduled functions) and that the VPS's weekly run pruned (`/var/lib/camsocs/status-full.json`: `"phase": "done"`, no `prune` failure; `docs/ops-vps.md`).
3. Delete or archive by hand what R1 and R9 leave to Joshua.
4. Re-read this schedule against `docs/data-model.md` and the privacy notice.
