# Retention schedule

What is kept, for how long, what ends it, and whether the deletion is automated yet. The public privacy notice (`/privacy`, "How long we keep it") states the same periods; change this file first, then the page and `PRIVACY_NOTICE_UPDATED` in `webapp/lib/site.ts`.

"Automated" means code in this repo enforces it today: the daily Convex cron `retention-daily` (04:15 UTC, `webapp/convex/retention.ts`; one paginated walk per rule, all with one clock), the talks pillar's own cron `talks-retention-daily` (04:30 UTC, `webapp/convex/crons.ts` → `ingest/talks:purgeExpired`), or the pipeline command `camsocs prune-cache`. Everything marked **manual** is Joshua's job; the reason is given.

| ID | Data | Kept for | Ends with | How it is removed | Automated? |
|---|---|---|---|---|---|
| R1 | Organisation listings (`organisations`, `orgCards`, teams, sessions) | While the organisation is active | No activity and no current register for 2 academic years → marked defunct, so `archived` (left out of the directory's default view), then deleted 1 year later. A removal request ends it at once (R8) | Status is derived daily (`convex/derive.ts`: `dormant` after 180 days without activity or a current registration; `archived` once defunct). Deletion: `ingest/purge:removeEntity` | `dormant`: yes. Archiving and deletion: **manual** — the first harvest was in October 2026, so nothing can be due before July 2028, and deleting a listing is a judgement call (a quiet society is not a defunct one) |
| R2 | Provenance (`fieldClaims`, `sources`). `fieldClaims.valueRaw` holds the unredacted original of public free text (D1), names included | As long as the entity it describes; the original of a superseded free-text reading only until a newer reading replaces it | Entity deleted; a newer reading | Deleted with the entity (`ingest/purge:removeEntity`); an event's claims go with the event (R3); a superseded free-text claim's `valueRaw` is cleared when it is superseded (`ingest/claims.ts`, DPIA-lite R-12) | With R1: **manual**. With R3 and supersession: yes |
| R3 | Events (`events`, `eventOrganisers`), stored event images | 1 year after the event ended (longer than the 180-day activity window that `lastActiveAt` needs) | Age | `purgeEvents`: the event, its claims (in pages of at most 2,000 per call; the event goes only once none is left) and organiser links; its stored image (and `storedFiles` row) unless another event or a logo still shows it; its organisers are re-derived | **yes** |
| R4 | Mailing-list messages (`inboundEmails`, their stored HTML and attachments), the mail's words quoted in its events' claims, the model's replies about it and its staged events | Body (text, HTML, attachments) and its words elsewhere: 30 days from receipt once processed. The row (sender, subject, extraction outcome): 90 days from receipt | Age; extraction finished | `stripMailBodies` empties the body, deletes the files (`bodyDeletedAt`) and clears the quotes and originals of every claim sourced `inbound:<message-id>`; `purgeMail` deletes the row and anything left in storage, processed or not — a mail its events cite stays as a stub (message id, list, receipt time, organisation, event keys; no sender, subject or text, `purgedAt`). On the pipeline host `prune-cache` (after every scheduled run) deletes the `email_events_v1` / `image_events_v1` replies, the calendar-noise verdicts and name redactions of mail-derived readings (cached apart as `event_noise_v2.mail` / `redact_names_v2.mail`) and `mailing_list_email` staging after 30 days | **yes** |
| R5 | Named committee members (`people`) | Until `staleAfter` (the next 30 June, D2) + 30 days, unless the person consented to longer | Handover date | `stale` set daily (`convex/derive.ts`); `expirePeople`: past `staleAfter`, the broker's own rows are archived (the 30-day grace, in which the broker may extend `staleAfter`); 30 days past it every row is deleted, from public sources or the broker's own, and its key is remembered (`expiredPeople`: key and academic year only) so a page that still lists last year's committee does not add it back; a re-sighting never moves `staleAfter` forward unless the source states a later academic year. Rows with `consentBasis: consent` stay. By hand, for officers of sensitive societies (DPIA-lite §5): `retention:removeOffSiteSensitiveOfficers` deletes a pipeline row whose source is not the society's own website (a dry run unless `apply: true`) | **yes** |
| R6 | Interactions and introductions | 3 years after the last interaction with that organisation | Age | `purgeInteractions`: an interaction 3 years old whose organisation has had none since; `purgeIntroductions`: introductions 3 years old | **yes** |
| R7 | Raw page cache (`var/cache/`), LLM inputs/outputs kept locally, staged observations (`var/staging/`, including the talks stage's `var/staging/talks/<run>.jsonl`, which holds speaker names), the pipeline host's run logs | 90 days | Age | `pixi run prune-cache` (`camsocs prune-cache --older-than 90d`): a page's body, meta and failure note go together once all are older; LLM replies one by one; superseded staging files, never the latest of each part (talks staging included, `pipeline/.../prune.py`). Run logs on the VPS (`/var/log/camsocs/`) are removed by logrotate at 90 days | **yes** on the VPS host: every scheduled run (daily and weekly) ends with `prune-cache` (`docs/ops-vps.md`, D5); on the laptop, when the command is run |
| R8 | Listing requests (`listingRequests`) | 2 years after resolution; a rejected request 90 days after it was rejected | Age | `purgeRequests` deletes the row — an accepted correction, which its `owner_submitted` claims cite, is reduced to a stub (key, kind, listing, role, outcome, dates; no submitter address, message or fields, `purgedAt`). Accepting a removal or objection creates **suppressions** (`suppressions`: the listing's key, a field name, an address only as a sha256, or a broker person's key; date and request kind), kept indefinitely: the pipeline filters by them before every load, and Convex refuses what slips through (`convex/lib/suppressions.ts`). The claims a suppression sets aside keep no value, original or quote (`setAsideBy`); lifting it deletes them | **yes** |
| R9 | Sign-in accounts and sessions (Better Auth) | Sessions: until expiry. Accounts: until deletion is requested, or 2 years unused | Expiry; request; inactivity | Better Auth expires sessions; account deletion by hand | Sessions: yes. Accounts: **manual** — they live in the Better Auth component's tables, which only its adapter should write; nobody but Joshua signs in before the `@cam.ac.uk` tier opens |
| R10 | Run log (`harvestRuns`) | 1 year | Age | `purgeRuns` | **yes** (no personal data) |
| R11 | Academic talks (`talks`, `talkDetails`): titles, speakers' names and affiliations as published, abstracts, venues (decision D7) | 30 days after the talk ended (`endsAt ?? startsAt`); a talk its source stops listing is marked `missing` and goes with the same rule | Age | `talks-retention-daily` (04:30 UTC) → `ingest/talks:purgeExpired`: a page of talks per scheduled mutation, each with its details (`TALK_RETENTION_DAYS = 30`, `webapp/convex/ingest/talks.ts`). A name or contact suppression (R8) also applies to talks: suppressed speakers are dropped and suppressed names and addresses cut from stored talks (`ingest/talks:scrubStored`). `departments`, `talkRuns` and `talkStats` hold no personal data (department registry, run summaries, counts) | **yes** |
| R12 | PostHog event data, project `camsocs` on EU Cloud: browser analytics and browser exceptions of visitors who accepted (P11), server-side errors and counts (P12), and the harvester's telemetry and LLM usage metrics (no personal data). The browser's events reach PostHog through `/relay`, which forwards no visitor IP, and client IP addresses are discarded at ingestion (project setting), so none is kept | Up to 1 year: the free plan's "1-year data retention" ([posthog.com/pricing](https://posthog.com/pricing), read 2026-11-01; "Any data stored for more than the retention period may be permanently deleted") | Age | PostHog says data older than the plan's retention "may be permanently deleted", so this is not a guarantee: the July check confirms nothing older remains, and anything older is deleted by hand. Withdrawing consent deletes the `ph_*` identifier from the visitor's browser (R13); the events already sent stay pseudonymous under it, the controller can no longer tell whose they are (UK GDPR Art 11), and they go with the rest | By the provider; **manual** check each July. ⚠ A paid plan raises retention to 7 years: before any plan change, decide the period, update this row and `/privacy`, or delete older data |
| R13 | On the visitor's device, not held by us: the consent record `camsocs-consent` (localStorage), PostHog's two `ph_*` cookies (`ph_<token>_posthog` and its metadata cookie `ph_<token>_posthog_cpm`), `ph_*` localStorage and sessionStorage keys and `__ph_opt_in_out_<token>` flag (only after "Accept analytics"), the palette's last 5 searches (`camsocs:recent-searches`) | Consent record: 180 days, then the banner asks again. `ph_*` cookies: 180 days from the last visit (`cookie_expiration: 180`, both renewed on each visit). sessionStorage: until the tab closes. `ph_*` / `__ph_*` localStorage: no expiry of its own; deleted on withdrawal, on the first page load after the choice lapses, or when the visitor clears site data. Recent searches: until the visitor removes them | Age; withdrawal ("Cookie settings" → "Reject"); the visitor clearing site data | Withdrawal deletes every `ph_*` cookie (current host and parent domain) and `ph_*` / `__ph_*` localStorage / sessionStorage key at once, and stops capture (ENG-2); every page load without a grant (unset, denied or lapsed) deletes them too (ENG-4, `startAnalytics`); the browser expires the cookies | **yes**, in the visitor's browser |
| R14 | Backups of the Convex production database (ENG-44): every table, the Better Auth component's (accounts, sessions, keys) and stored files, as snapshot ZIPs on the VPS host (`/var/lib/private/camsocs-backup/`, `0700` root, only the backup's own systemd user and root can read them; `docs/ops-vps.md` §10). Whatever the other rows keep, as it stood that night | The newest 14 nightly backups, so normally 14 days; while backups fail, the last 14 stay until a new one succeeds. Convex's own dashboard backups, if made: 7 days (manual, daily) or 14 (weekly), by Convex | Age (a newer backup); a deleted row or a suppression reaches the backups as the old ones age out | The nightly `camsocs-backup.service` deletes all but the newest 14 after each good backup (`CAMSOCS_BACKUP_KEEP`). A restore brings back what was deleted after the backup was taken: the restore procedure re-applies every deletion and suppression since then (`docs/deploy.md` §8) | **yes** |

## Annual review (each July)

1. Refresh every listing from its sources (`pixi run harvest`); anything no source still lists becomes a candidate for archiving (R1).
2. Check that `retention-daily` ran (Convex dashboard, scheduled functions) and that the VPS's weekly run pruned (`/var/lib/camsocs/status-full.json`: `"phase": "done"`, no `prune` failure; `docs/ops-vps.md`). Backups (R14): on the host, `ls /var/lib/camsocs-backup/` holds no more than 14 `convex-prod-*.zip`, the newest from last night, and `status-restore-test.json` says `"result": "ok"` from the last Monday.
3. Delete or archive by hand what R1 and R9 leave to Joshua.
4. Re-read this schedule against `docs/data-model.md` and the privacy notice.
5. PostHog (R12): the organisation is still on the free plan (1-year retention) or the new period is recorded here and on `/privacy`; client IP data still discarded, session replay still off, PostHog AI still off at organisation level (`docs/deploy.md`, "PostHog (monitoring)").

## Open items

- R1 archiving and deletion, and R9 account deletion, stay manual (reasons above).
- A removal or takedown that arrives by email (a rights holder writing as `/about#copyright` asks, or anyone writing to the contact address) is entered through `/request` as a `remove` or `object` request for the listing, on the sender's behalf, and accepted in the broker, so that a suppression is recorded (R8). Answering the email alone records nothing, and the next harvest brings the material back. An event can only be suppressed whole, its image with it. Talks have no suppression beyond names and contacts (DPIA-lite R-14): a request about a talk's title or abstract goes to its organiser, and the talk follows its source.
- R12 depends on PostHog's plan, not on code here: PostHog says older data "may be" deleted, so the July check confirms nothing older than a year is still queryable.
- `prune-cache` runs only where it is scheduled: the VPS runner prunes weekly once installed (PLAN.md J8); until then, and for the laptop's own `var/`, run `pixi run prune-cache` by hand.
