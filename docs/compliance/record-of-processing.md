**Conclusion (research of 2026-11-01; not legal advice):**

- PECR reg 6, as substituted on 5 Feb 2026 by DUAA 2025 s.112 (commenced by S.I. 2026/82 reg 2(w)), forbids storing or accessing information on a device, localStorage included and not only personal data, unless the user consents or an exception in Schedule A1 applies ([reg 6](https://www.legislation.gov.uk/uksi/2003/2426/regulation/6), [Sch A1](https://www.legislation.gov.uk/uksi/2003/2426/schedule/A1), [S.I. 2026/82 reg 2](https://www.legislation.gov.uk/uksi/2026/82/regulation/2/made), [ICO: how PECR relates to the UK GDPR](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/how-do-the-pecr-rules-relate-to-the-uk-gdpr/)). An analytics SDK reads device and browser properties even without cookies, so reg 6 applies to it in any mode ([ICO: what are storage and access technologies](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-storage-and-access-technologies/)).
- The DUAA statistical-purposes exception (Sch A1 para 5, in force 5 Feb 2026) is **not relied on**: it fails once a visitor objects (para 5(1)(e)), the ICO says it is lost if "individual-level information" is retained after aggregation, which PostHog's event rows are, and PostHog's DPA lets it use data for "service improvement, benchmarking" (cl. 1.1.14), which strains para 5(1)(c) ([ICO: what are the exceptions](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-the-exceptions/), [PostHog DPA](https://posthog.com/dpa)). Hence posthog-js is not loaded at all before "Accept analytics"; there is no cookieless mode and no IP/UA hashing (the ICO treats hashed identifiers as identifiers).
- Consented analytics therefore rests on consent under the UK GDPR too; legitimate interests must not be used as a fallback where consent is required ([ICO](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/how-do-the-pecr-rules-relate-to-the-uk-gdpr/)). The banner follows the ICO's consent rules: equal Accept and Reject, nothing before a click, silence is not consent, PostHog named with purpose and lifetime, withdrawal as easy as consent and the stored `ph_*` data removed, choices re-asked after at most six months (180 days) ([ICO: managing consent in practice](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/how-do-we-manage-consent-in-practice/)).
- The consent record is exempt as strictly necessary (Sch A1 para 4(2)(e)(ii); the ICO accepts consent-preference cookies as exempt if used solely for that purpose).
- Server-side error tracking and counts (P12) store nothing on and read nothing from the device, so reg 6 is not engaged; nothing from request headers is stored except `page_visit`'s kind-of-site category, derived from the `Referer` header (one of nine fixed values; the header itself is never stored or sent), which narrows but does not wholly sidestep the open question whether headers are information "automatically emitted by the terminal equipment" (reg 6(2)(b); **unverified**, no ICO text on it). Their basis is Art 6(1)(f) (LIA §D).

## Security measures (Art 32, summary)

- Broker and internal tables reachable only through functions that call `requireBrokerUser`; public queries return validated projections only (`convex/lib/projections.ts`, `returns` validators).
- Pipeline writes only through `/api/pipeline/*` with a Bearer key; secrets live in `pipeline/.env` and the Convex env, never in Git.
- On the VPS host (D5) the pipeline runs as its own unprivileged user under sandboxed systemd units (`ProtectSystem=strict`, `NoNewPrivileges`, no capabilities, Mya's agent data and Docker unreachable, private address ranges denied), with its env files `0600`, a read-only deploy key and its own cliproxy key; it is not run inside the LLM agent's container, and its fetcher never connects to a non-public address (`docs/ops-vps.md`). A failed run's Slack alert carries structured facts only (group, exit code, phase, commit, run key, failed stages' names, the log's path): no personal data goes to Slack, so Slack is no recipient here.
- `cam_only` events need a verified `@cam.ac.uk` session; `members_only` events are never shown.
- Backups of Convex production (ENG-44, R14) on the VPS host: made by a sandboxed systemd unit as a dynamic user of its own (never root or the harvest's user) with a production deploy key allowed only to back up and read; kept `0600` in a `0700` directory under `/var/lib/private`; restore-tested weekly into a throwaway backend on the loopback; the journal, status files and Slack alerts carry table names and counts only (`docs/ops-vps.md` §10).
- Personal data breaches: `breach-procedure.md` (detect, contain, assess, the 72-hour Art 33 test, Art 34 notice, a log kept outside Git); security contact security@camsocs.uk, published on `/about#security`, `/privacy` and `/.well-known/security.txt`.
- TLS everywhere; no advertising or third-party trackers. Analytics (P11) is first party: posthog-js loads only after consent and sends through the site's own `/relay` path; the PostHog project discards client IP data and has session replay off (`docs/deploy.md`, "PostHog (monitoring)"). Secrets for PostHog live in the 1Password Mya vault, never in Git.
